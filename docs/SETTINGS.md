# Settings

Precedence is the usual one: a command-line flag, then the environment, then a file.

| Variable | Default | Meaning |
|---|---|---|
| `FBTODO_HOME` | — | one directory for state, locks and logs, overriding the XDG default below |
| `XDG_STATE_HOME` | `~/.local/state` | state lives in `$XDG_STATE_HOME/fbtodo`; a legacy `~/.freebuff` is moved there once, when no watcher holds it |
| `FBTODO_NOTIFY` / `_DROP` / `_ASK` / `_PAUSE` / `_PANE_BELL` | `~/.config/freebuff-notify/*.py` | the five watches |
| `FBTODO_ASK_SECONDS` / `_PAUSE_SECONDS` / `_PANE_BELL_SECONDS` | 3 / 30 / 60 | their cadences (0 = never) |
| `FBTODO_PANE_SECONDS` | 3 | how often the keeper looks |
| `FBTODO_SOURCE_SETTLE` / `_BUILD_CHECK` | 2 / 1 | the **reload clocks**: how long a source write is waited out before it is believed, and how often the pane, the keeper and the watcher each ask whether they are still the build on disk. Lowering the first is a real trade — a save still landing can be exec'd into, which is why the default is what protects an editor — and it is here for a caller that swaps in a complete copy of the build (the self-check sets `0.2` / `0.1`) |
| `FBTODO_SPLIT` / `FBTODO_PANE_SIZE` | `v` / `12` | where the pane opens — `left`/`right`/`top`/`bottom` (which fix the edge), or `h`/`v` for the splitter's own trailing edge (right / below) — and its size |
| `FBTODO_NO_PANE` | — | set to disable panes entirely |
| `FBTODO_PATCH_LOG` / `_META` / `_ALERT_LOG` | `~/.config/freebuff-patch-watch/watch.log`, `~/.config/manicode/freebuff-metadata.json`, `~/.config/freebuff-notify/phone.log` | the optional `PATCH`/`ALERT` row |
| `FBTODO_ACCENT` / `_ACTIVE` / `_SUCCESS` / `_FAINT` / `_MUTED` / `_TRACK` | theme | palette overrides |
| `FBTODO_GRADIENT_START` / `_END` | theme | `#rrggbb`, or a raw SGR code like `1;36` for the accent |
| `FBTODO_TRUECOLOR` | auto | force 24-bit colour on or off |
| `FBTODO_TMUX` | `tmux` | the tmux binary/args to drive (a test knob) |
| `FBTODO_PATH` | the opener's `PATH` | the base of the `PATH` handed to a pane in its own command line, instead of whatever the tmux server would rebuild (the interpreter's own directory is always put first, so anything the pane resolves by name is the same Python). Set it when a machine needs a specific one; a pane that was opened pinned passes this value on |
| `FBTODO_LABEL_FLOOR` | `10` | estimates: a finished span under this many seconds is not evidence — it sets no pace and moves no memory (`0` keeps every span, the pre-4.23.0 behaviour) |
| `FBTODO_BLEND_WEIGHT` | `0.5` | estimates: how much a *waiting* step's number comes from its wording rather than the list's pace, `0`–`1` (`0` = pace only; `1` = wording only, which drops the pace and mis-sizes the tail) |
| `FBTODO_GOAL_LINES` | `3` | how many lines the goal heading may take (`0` hides it) |
| `FREEBUFF_PHONE` | on | `off` / `0` / `false` / `no` / `disabled` mutes the phone, read when a bell sends; the notify kit's `phone-state` file, the pane's `m`/`u` keys and `fbtodo mute on|off` write the same word to the same place |
| `FBTODO_NOTIFY_DIR` | `~/.config/freebuff-notify` | where the pane's mute key and `fbtodo mute` write the kit's two switch files (`phone-state` for `phone.sh`, `state` for `bell.sh`) |
| `FBTODO_PANE_KEYS` | on | `off` / `0` / `false` / `no` mutes the pane's KEYBOARD: `m`, `M`, `u`, `n` and `p` stop acting, and a pane opens with the terminal as it found it (`--no-keys` says the same thing) |
| `FBTODO_PANE_MOUSE` | on | `off` / `0` / `false` / `no` leaves the MOUSE to the terminal, so the pane never asks for click reporting and its ntfy button is worked by `n` alone — the opt-out for a reader who wants to select text with the mouse (`--no-mouse` says the same thing) |
| `FBTODO_PIP_PID` | `~/.cache/fbtodo/pip.pid` | where `fbtodo pip start` writes the floating window's pid, so `pip stop`/`pip status` find the window this shell started (a pid file naming nobody is not a running window) |
| `FBTODO_PIP_PIN` | `~/.cache/fbtodo/pip-pin` | where her TAUGHT pin lives (a taught pin outranks the measured fit below) — a plain `x,y` offset from the top-left corner of the window the pane is in, written when she is dragged and pinned again (`p` while free, then `p`), and re-read twice a second so a rewrite moves her on the next tick. No file means the middle of that window; `fbtodo pip forget` removes it |
| `FBTODO_PIP_FREE` | `~/.cache/fbtodo/pip-free` | the switch file for her PIN: while it exists she is draggable and stays where she is put, and it is removed to pin her back over the pane's own middle. The pane's `p`, `fbtodo pip free|stuck` and the running window all read the same file |
| `FBTODO_PIP_SLACK` | `~/.cache/fbtodo/pip-slack` | where the PANE publishes its own grid for her window to read: `rows cols start count epoch` (the pane's grid, the first row its frame left blank, how many rows that is), written only when the numbers change. Her window stands in those rows — the space the ASCII picture used to be drawn in — and uses `cols` a second time, to pick the pane out of a screenshot: a candidate rectangle whose width is nothing like `cols` cell-widths for the height it claims is passed over (the explorer sidebar was a better-looking pair of vertical lines than the pane was). The file is how the pane says what a screenshot cannot (its background is transparent onto a wallpaper) |
| `FBTODO_PIP_ROWS` | `-1` (her panel's own size) | how many rows the pane RESERVES for her floating window while it is running, so she stands in blank space instead of on a step: `-1`/`auto` (and unset) is as many as her drawn panel would have taken (`buffy_panel_rows` — bounded so the steps keep `BUFFY_LIST_FLOOR` rows, and a pane too short for both keeps the list), `0`/`off` reserves nothing (she then has only the slack the list happened to leave, and steps out when it left none), a number is exactly that many rows. Her window is fitted into the slot at a whole number of art pixels and never drawn outside the pane |
| `FBTODO_PIP_MOOD` | `~/.cache/fbtodo/pip-mood` | where the PANE publishes what she is FEELING — including `wait`, the turn-ended "waiting for you" state she HOLDS a pose for (the whole table of moods and when each one shows is [MOODS.md](MOODS.md)), in `buffy_mood`'s own words — the same word that picks the face on the pane's top border, so the picture in her window and the border cannot disagree about the same list. One line, rewritten only when the mood changes and again if the file has gone missing. Her window reads it twice a second and wears the POSE that word means (`moodCycles` in `scripts/buffy-pip.swift`: `work`, `done`, `idle`, `none`, `error`, `nudge`, `stale`, each a short cycle at its own pace, and the last three hold still) |
| `FBTODO_PIP_BUBBLE` | `1` | whether she TALKS: a MANGA balloon built AROUND the line — the words are measured first, so a longer line is a wider cloud and one that wraps is a taller one — drawn INSIDE her own square (never over the pane's list, never outside the pane, whatever the layout does) with one short line per mood, picked at random and never the one she just said. The mood chooses the shape: a soft pink cloud while she works, the roundest and sparkliest one when the list is done, a row of detached thought dots while she is only thinking, waiting or left over, and a jagged SHOCK balloon for `error` and `nudge`. A line goes up when her MOOD changes and at most once every `FBTODO_PIP_BUBBLE_GAP`; the one that is worth interrupting her silence for is a FINISHED list, which always gets a line and a burst through her own poses (so "every step is ticked" is something you can see rather than read). `--bubble 0` / `off` / `no` / `false` / `none` takes the bubble away, and a mood with no line says nothing at all |
| `FBTODO_PIP_BUBBLE_GAP` | `20` | seconds she stays quiet after a line (`--bubble-gap`). The line itself stands for 5 s on its OWN clock rather than `FBTODO_PIP_TRANSITION`, because two words are read at a glance and ten seconds to read them is not a transition — it comes up at full strength with the POP (`FBTODO_PIP_POP`) and fades OUT only over 0.35 s, and it hangs on the other side of her head than the last one did, so her ahoge is not covered by every single line |
| `FBTODO_PIP_SURPRISE` | `0.12` | the chance that a mood change gets the SURPRISE instead of the line that mood would have said (`--surprise`): words that belong to no mood, in the one balloon that is all of them at once — spiked, spangled and dotted, in violet. It is a POSE too: she wears a sticker from OUTSIDE her mood's own cycle for as long as the line lasts (it arrives as a cut, because a surprise you can see coming is not one, and it dissolves back to the step she left, which held still for it). `0` is never and `1` is every time; the pane never asks for it, so it can arrive on any word it publishes, and her log says `surprise=yes pose=15` on the line that was one. See `--art-surprise` for looking at one without waiting for luck |
| `FBTODO_PIP_POP` | `0.34` | how long her balloon takes to POP into place, in seconds (`--pop`): it arrives squashed and springs open, which is what tells the eye something NEW appeared — a fade in and a fade out were the same movement, so the two were told apart only by watching the whole half-second. It is anchored at the balloon's top edge and never scales wider than the settled cloud, so a pop can only grow inward and can never leave her square. `0` turns it off |
| `FBTODO_PIP_LINES` | `~/.cache/fbtodo/pip-lines` | the FILE her chat lines come from (`--lines-file`), re-read while she runs on her pin tick — the same deal the mood table has, so a joke is a text file and not a rebuild. One row per line she may say: the mood, a TAB, the words (`work\tchop chop`); `#` starts a comment and a name the pane cannot produce is ignored. A mood the file does not name keeps the built-in lines, and a row with NO words clears that mood's lines — which is how "she says nothing in this one" is written down. `surprise` is a key here too, for the lines that belong to no mood. `fbtodo-pip --lines` prints the effective table in exactly this shape, so a redirect seeds a file to edit |
| `FBTODO_PIP_TUNE` | `~/.cache/fbtodo/pip-tune` | the FILE every knob above lives in (`--tune-file`), written for you by `fbtodo pip tune` — her window re-reads it on its pin tick, so a knob set from the shell is worn without a restart. One `name value` per row, the names being the flags' own (`transition`, `pose-min`, `bubble`, `bubble-gap`, `surprise`, `pop`, `fit-every`, `fit-retry`, `side`, `tick`), and the PRECEDENCE is the usual one: a flag beats an environment variable, an environment variable beats this file, and this file beats the default. `fbtodo-pip --tune` prints every knob with the value she would run with, where that value came from and whether a change is live |
| `FBTODO_PIP_MOODS` | `~/.cache/fbtodo/pip-moods` | her MOOD TABLE as a file — `name frames ms` per line, exactly the shape `fbtodo-pip --moods` prints, so `fbtodo-pip --moods > ~/.cache/fbtodo/pip-moods` and an editor is the whole retune (no rebuild, no restart: her window re-reads it on the next half-second tick and says so in her log). A file that names only some moods is an OVERRIDE — the rest keep their built-in rows; a row naming a mood the pane cannot produce, or whose frames are all past the end of the art, is ignored whole rather than leaving her without a pose. `--moods-file PATH` is the same knob on her command line, and deleting the file puts the defaults back |
| `FBTODO_PIP_HOST` | `Freebuff` | the app whose window is her home WHEN the pane's own process chain cannot say — the chain is what is used whenever `fbtodo pip start` could read one, since it names the window on any terminal. An empty value pins her to the middle of the screen, which is also the fallback when no window is found |
| `FBTODO_BUFFY_ROWS` | unset (none) | whether the PANE draws buffy-chan at all: unset / `0` / `off` is a pane that is only the list, which is the default because her picture is in a window of her own (`fbtodo pip start`) pinned over that very pane — `-1`/`auto` sizes the drawing to the pane and a number is exactly that many rows (still bounded so the steps keep `BUFFY_LIST_FLOOR` rows) |
| `FBTODO_BUFFY_STYLE` | `blocks` | the grid her in-pane picture is drawn in, when `FBTODO_BUFFY_ROWS` asks for one: `blocks` (a cell is one pixel wide and two tall, the lower pixel in the cell's background) or `braille` (a 2×4 dot grid) |
| `FBTODO_BUFFY_ZOOM` | `1.0` | how much of her the in-pane picture shows: `1.0` is the whole character, larger values push in on her face |
| `FBTODO_PIP_BIN` | `~/.cache/fbtodo/bin/fbtodo-pip` | where `scripts/buffy-pip.sh` builds/loads her window (a build product, kept out of the checkout) |
| `FBTODO_BUFFY_DIR` | `assets/buffy/pip` | the frames her window and her in-pane picture are read from. The window prefers `assets/buffy/pip` — the same twenty poses at 384px, which is exactly the pixel size she is drawn at (192pt at 2x), so nothing is resampled — and falls back to `assets/buffy` (128px, what the PANE's picture is averaged from) on a checkout that has not run `scripts/buffy-thumbs.py --size 384`; the pane's own picture always reads the small set |
| `FBTODO_PIP_SHARP` | `1` | whether her frames are resampled off the screen (`renderedArt`: Core Image Lanczos plus a light unsharp mask, once, at the exact device pixel size, then drawn 1:1 with interpolation off) or handed to the drawing path to scale (`0`/`off`/`no`/`false`/`none`). Only a size that is not the art's own is resampled at all, so the knob does nothing while she is drawn 1:1 |
| `FBTODO_PIP_TRANSITION` | `10000` | how long she takes to get from one state to the next, in ms (`--transition`): the slot the pane's layout moved her into is EASED over it, the window fades OUT over it (ARRIVING is a cut at full opacity — "also remove fade in" — and `--transition 0` is the only other cut), and a change of pose is a CROSS-DISSOLVE of the same length. One number for all three, because all three are the same question — "how long is the transition" — and it is meant to be SEEN, so **any value below 10 s is raised to 10 s**; `0` is the one value that is not a length, and it is every one of them as a hard cut (the behaviour she started with, and the A/B arm). A value that is not a number is the default. The SLIDE is a slide: her size is settled the moment a move begins and only her corner travels, so she is never the wrong size for her slot on the way. A POSE is capped at one step of the mood it is arriving at — a mood that steps every 900ms cannot dissolve for ten seconds without being a permanent smear — but never made fast by that cap, so it is `min(transition, max(pace, FBTODO_PIP_POSE_MIN))`: the slow length you can watch, and a fast mood that still settles. A mood that HOLDS has no step to cap against and takes the whole transition. While a move is in flight her frames are not re-rendered for the sizes she is passing through |
| `FBTODO_PIP_POSE_MIN` | `10` | the floor under the pose cap above, in seconds (`--pose-min`): a pose change takes at least this long however fast its mood steps, because the whole point of the transition is a change you can watch — and it is now the transition's own length, so a pose is NEVER the fast one the owner kept catching (2026-10-07: "increase default transition per pose up, i dont want it to be too fast"). Set it to `0` to let a fast mood dissolve only as long as its own step |
| `FBTODO_PIP_FIT_EVERY` | `4` | seconds between the pane being re-measured off a screenshot of the window (`--fit-every` is the same knob on her command line) |
| `FBTODO_PIP_FIT_RETRY` | `1.5` | seconds before a measurement that found NOTHING is tried again (`--fit-retry`). Its own, much shorter clock because that is the state she comes BACK from — a minimize, a window that has not redrawn, a pane mid-frame — and a whole `FIT_EVERY` spent there is the delay the owner saw after restoring a minimized window. A window that returns to the screen is measured on the next tick whatever either clock says |
| `FBTODO_PIP_SIDE` | `192` | the size she asks for, in points (`--side`, also honoured in the environment when the Swift is run on its own); the pane's own slot always wins — it is fitted to the empty rows below and snapped to a whole number of art pixels, so this is a ceiling, not a promise |
| `FREEBUFF_NO_REFRESH` | — | the `fb` launcher skips its `npm i -g freebuff` round trip |

A pane is handed the settings that decide **where it works and where its bells go**, not left to
inherit them: tmux starts a pane from its server's environment, so `FBTODO_HOME`, `XDG_STATE_HOME`,
`FBTODO_TMUX` and the six watch paths (`FBTODO_NOTIFY`, `_DROP`, `_ASK`,
`_PAUSE`, `_PANE_BELL`, `_LOCKS_BELL`) are written into the pane's own command line — beside the
pinned interpreter and `PATH` — by both `pane_command` and the `fb` launcher. Each rides only
when it is set, and because the value is in the command string a `tmux respawn-pane` (or the
keeper's repair) brings it back rather than the server's. Without that, a server started before
the owner exported one of them would leave the pane reading another state root, following another
set of sessions, or ringing the default bells instead of the ones this machine installed. A pane
whose recorded command is an **older pin** — one of these keys missing or carrying an old value —
is upgraded by the keeper on the next pass, so an answer the build no longer writes does not
outlive it; only the carried values are compared, so an `fb` pane on `--instance-of` that names
all of them is left alone.

Pane repair has a per-pane switch that is not an environment variable, because the pane is
the scope: the tmux user option **`@fbtodo_repair`** turns the keeper's automatic respawn of a
pane whose interpreter drifted off for that pane — `tmux set -p -t %3 @fbtodo_repair off`, or
`-w` / `-g` for a window or the whole server, since tmux resolves the option up the chain.
`off` / `no` / `0` / `false` disable it; anything else, or unset, leaves the repair running.
The pane is diagnosed either way — the keeper logs what it saw and the running pane shows
`KEPT (was on …)` on its title chip for a few seconds — but it is not respawned, and `on`
resumes the repair on the next pass with no keeper restart. `fbtodo keep off` / `on` /
`default` is that option as a command: the pane you are in, or one named with `--pane %3`;
one window with `--window TARGET` (a session, `session:index` or a window id — resolved
through tmux, and it outranks the server while a pane's own choice outranks it); and
`--server` for every pane at once (`keep` with no verb prints what is in force). The tmux
incantation is never needed.

The two estimate knobs are flags as well, so they can be set per run rather than per shell:
`--label-floor SEC` and `--blend-weight W`. Both are forwarded to the watcher when it is
started, so `fbtodo --label-floor 0 daemon` really does keep every span. Raising the floor
makes the estimates calmer (short flips stop setting the pace); lowering the weight makes the
pane trust the list's own pace over what a step's wording suggests. The reasoning behind both
is in [ESTIMATES.md](ESTIMATES.md).

Theming is a file, not a flag: `~/.config/fbtodo/theme.json`, overridden by
`./.fbtodo-theme.json` in the working directory, overridden by the environment above.

## Exit codes

`0` ok · `2` usage (argparse, including polling without a TTY) · `64` a bad `-s` value or
unexpected arguments · `65` a `push` payload that is not a state · `66` no instance, no
store, or nothing on stdin · `73` cannot create · `74` I/O error · `75` the watcher failed to
start · `78` a config or notifier error · `130` SIGINT · `141` SIGPIPE.
